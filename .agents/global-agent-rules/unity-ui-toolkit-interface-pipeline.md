# Pipeline создания runtime UI на Unity UI Toolkit

## Цель

Сначала согласовать финальный вид интерфейса в HTML, затем точно перенести его
в Unity UI Toolkit. Pipeline не требует промежуточных прототипов, которые
заведомо далеки от конечного результата.

Обязательных согласований два:

1. финальный HTML;
2. готовая версия в Unity.

## 1. Референсы по стилю

- Изучить предоставленные visual references.
- Если референсов недостаточно для выбора стиля, запросить их у человека.
- Выделить только применимые правила: цвет, типографику, форму панелей,
  слотов, иконок, состояний и эффектов.
- Не копировать чужие runtime assets без разрешения.

Результат: понятное направление стиля без обязательного отдельного отчёта.

## 2. Мокап и функции интерфейса

- Изучить дизайн-документ, мокапы, copy, состояния и правила взаимодействия.
- Если мокапа или функционального описания недостаточно, запросить недостающее.
- Считать предоставленный мокап layout-контрактом: расположение, размер,
  пропорции и связи элементов воспроизводятся минимум на 95%, если человек
  явно не разрешил переосмысление.
- Не добавлять подписи, подсказки, controls, decorative blocks или состояния,
  которых нет в запросе и мокапе.
- Спорную непрошенную деталь добавлять только после согласования, даже если
  агент с уверенностью 80%+ считает её полезной.

Для Minecraftorio особо важно:

- progress производства источника, верстака и печи имеет форму стрелки и
  заполняется слева направо;
- fuel progress печи имеет форму огня и заполняется снизу вверх;
- стрелки располагаются между input/recipe и output и не перекрывают слоты;
- approval prototype использует настоящие предметные иконки, а не буквы или
  текстовые заглушки;
- вспомогательная copy отсутствует, если её нет на мокапе.

Результат: подтверждённый состав экранов и точный layout target. Отдельные
`flow.md`, state matrix или служебный отчёт создаются только когда без них
реально нельзя безопасно реализовать сложное поведение.

## 3. Дизайн-система

Собрать минимальную систему, необходимую текущим экранам:

- semantic colors и typography;
- spacing и размеры;
- panel, slot, button и progress shapes;
- default, hover, selected, disabled и необходимые drag/drop states;
- правила иконок и scaling для целевых разрешений.

Не создавать компоненты, tokens или варианты «на будущее».

## 4. Финальный HTML в Open Design

- Собрать только финализированный HTML/CSS/JS prototype.
- Показать все запрошенные экраны в настоящем визуальном качестве.
- Использовать реальные финальные или оригинальные временные иконки, которые
  визуально представляют предмет, а не текстовые сокращения.
- Проверить объявленные viewport, русский текст и ключевые состояния.
- Открыть prototype в Open Design и запросить согласование.

### Approval 1 — HTML

До согласования запрещено переносить UI в Unity.

Человек утверждает:

- сходство с мокапом;
- стиль и дизайн-систему;
- расположение элементов;
- иконки, progress shapes и состояния;
- required screens и viewports.

## 5. Перенос в Unity

После approval HTML:

- перенести structure в UXML, visuals в USS, bindings/commands в C#;
- сохранить утверждённый layout и внешний вид без скрытого упрощения;
- использовать retained-mode lifecycle: setup в `OnEnable`, cleanup в
  `OnDisable`, без построения или polling UI в `Update`;
- соблюдать input isolation, pointer capture/release и архитектуру проекта;
- проверить поведение, Console и целевые разрешения;
- сравнить Unity с утверждённым HTML side-by-side.

Техническая заметка или mapping создаётся только для реального unsupported
effect или нетривиального workaround. Полный обязательный mapping/report не
нужен.

### Approval 2 — Unity

Человек утверждает готовый интерфейс непосредственно в Unity. Отличия от HTML
должны быть заранее показаны и объяснены.

## Минимальная проверка

- все запрошенные функции работают;
- UI events не протекают в gameplay;
- drag/drop корректно завершается и отменяется;
- нет новых Console errors;
- layout проверен в объявленных viewport;
- визуал соответствует утверждённому HTML и исходным мокапам.

Автоматические tests и captures добавляются пропорционально риску. Не нужно
создавать отдельный QA-файл для каждой проверки.

## Правило scope

Делать только явно запрошенное и минимально необходимое для его работы. Не
расширять интерфейс, конфиги, документацию или архитектуру ради полноты.

Если непрошенная деталь кажется необходимой с уверенностью 80% или выше,
сначала описать её человеку и дождаться согласования. При меньшей уверенности —
не добавлять.
