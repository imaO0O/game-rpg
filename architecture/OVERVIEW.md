# Технические границы проекта

Долгоживущие решения. Менять их дорого, поэтому каждое записано вместе
с причиной и с тем, что было отвергнуто.

## Движок и рендер

**Unity 6000.5.10f1, HDRP 17.5.0.**

HDRP выбран автором вместо URP ради объёмного тумана и видимого конуса
света из фонаря — в тёмном доме это половина атмосферы. Машина тянет:
RTX 5070, Ryzen 5 7500F, 32 ГБ.

Следствия, с которыми живём:
- **WebGL недоступен.** HDRP собирается только под настольные платформы.
  Целевая платформа — Windows. Модуль WebGL в редакторе стоит, но не
  используется.
- Итерация медленнее, чем на URP: компиляция шейдеров и запекание света
  занимают ощутимое время. Планировать запекание пакетами, а не по одному
  светильнику.
- Проект развёрнут из локального шаблона `3d-high-end` (HDRP), а не собран
  вручную: в нём уже настроены Quality-ассеты Balanced / High Fidelity /
  Performant и профиль неба и тумана.

## Пакеты

Ставим по конкретной нужде, не «на будущее».

| Пакет | Зачем |
| --- | --- |
| `render-pipelines.high-definition` | Рендер |
| `inputsystem` | Ввод, клавиатура + геймпад |
| `probuilder` | Геометрия дома и простая мебель прямо в редакторе |
| `feature.development` | Test Framework и интеграция с IDE |
| `ugui` | Неявная зависимость части подсистем |

Убраны из шаблона: `visualscripting` (общие правила запрещают no-code
графы в рантайме), `collab-proxy` (версионирование — обычный git),
`timeline` (понадобится не раньше финальной сцены — тогда и добавим).

## Ассембли

Четыре, больше — только по измеренной причине.

```
Game.Runtime          (ссылается на Unity.InputSystem)
Game.Editor           → Game.Runtime, только редактор
Game.Tests.EditMode   → Game.Runtime, только редактор
Game.Tests.PlayMode   → Game.Runtime
```

Ассембли на фичу не заводим: на проекте такого размера они дают только
лишние границы.

## Разделение кода

- **Правила — обычные C#-классы.** `GameState`, каталог осколков, расход
  батареи, последовательность скримера. Тестируются без запуска сцены.
- **MonoBehaviour — только жизненный цикл, привязка к сцене и подача.**
- **ScriptableObject — только для авторского содержимого, которое реально
  переиспользуется.** Не обёртка вокруг каждого значения.

Ни менеджеров, ни синглтонов, ни шины событий, ни DI, ни локатора служб —
пока не появится конкретная нужда. Единственный объект, переживающий смену
сцен, — `GameSession`.

## Сохранение

Обычный JSON в `Application.persistentDataPath/save.json`. Формат должен
чиниться руками, поэтому — плоские списки, а не словари, и поле `version`
с первого дня.

Модель состояния держим в списках и на стороне C#, чтобы обойтись
`JsonUtility` без внешней библиотеки сериализации.

## Ничего не строится кодом в рантайме

Меши, свет, партиклы, коллайдеры, материалы — в префабах и сценах.

Причина названа прямо: в предыдущей реализации на Godot всё это собиралось
процедурно в `_ready()`, и визуал стало невозможно итерировать — правка
внешнего вида требовала правки кода и перезапуска. Для хоррора, который
на 80% состоит из света и звука, это оказалось смертельно.

Исключение — только то, что по своей природе вычисляется: положение
убегающего осколка, задержка отражения, кривая расхода батареи.

## Разделение контента

Код знает идентификаторы. Содержание — фотографии, голосовые, подписи,
названия мест — живёт в `private/` и в git не попадает. В репозитории
остаётся заглушечный каталог, чтобы каркас работал без контента.

Каталог осколков — `Assets/StreamingAssets/private/shards.json`.
StreamingAssets выбран потому, что папка целиком копируется в сборку
и читается как обычный файл в рантайме.

```json
{
  "shards": [
    { "id": "night_01", "caption": "Двор ночью", "area": "Рязань ночью" }
  ]
}
```

Формат — список, а не словарь, как было в Godot-версии: `JsonUtility`
не умеет словари, а тянуть ради этого стороннюю библиотеку сериализации
незачем. Если старый `shards.json` сохранился, его нужно один раз
переложить в этот вид.

Файла нет — каталог сообщает об этом один раз и работает на заглушках.
Без осколков игру всё равно можно проходить, а падать на пустой папке
незачем.

## Интерфейс

UI Toolkit, retained mode: настройка в `OnEnable`, уборка в `OnDisable`,
никакого построения UI в `Update`. Порядок работы —
`.agents/global-agent-rules/unity-ui-toolkit-interface-pipeline.md`,
с двумя согласованиями: финальный HTML, затем реализация в Unity.

## Автоматизация

Официальный Unity CLI — основной транспорт:

```
"C:\Program Files\Unity\Hub\Editor\6000.5.10f1\Editor\Unity.exe" \
  -batchmode -quit -projectPath D:\game-horror-3d -logFile <файл>
```

Тесты — тем же способом, через `-runTests -testPlatform EditMode|PlayMode`.
